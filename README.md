# Cheng Wei, Wang

Personal site and journal. Astro (static), a scroll-driven three.js particle
field, GSAP parallax and Lenis smooth scrolling.

Every page is pre-rendered to static HTML — search engines get the full content
without running any JavaScript — while the WebGL scene persists across
navigations so it never restarts.

## Run it

```bash
npm install
npm run dev      # http://localhost:4321
npm run build    # → dist/
npm run preview  # serve the production build
npm run check    # type-check .astro files and content schemas
```

Astro 7 runs the dev server as a background daemon. `astro dev stop`,
`astro dev status` and `astro dev logs` control it.

## Adding a work

Create a `.md` or `.mdx` file in `src/content/works/`. The filename becomes the
URL. Frontmatter is type-checked at build time, so a typo fails the build rather
than shipping silently.

```yaml
---
title: Project name
category: website          # website | web-game | brochure-video | arduino
year: "2018"               # free text, or "" to omit the row
overview: >-
  One or two sentences. Used as the lead paragraph on the detail page,
  the blurb in listings, and the meta description.
role: Full Stack programming
coworkers: ["Someone", "Someone else"]   # [] to omit the row
link:
  url: "https://example.com"             # "" to omit
  label: "example.com"
  status: live                           # live | demo | deprecated | none
cover: /works/project/cover.jpg          # optional
featured: true                           # surfaces on the landing page
order: 1                                 # lower sorts first
---
```

Images go in `public/works/` and are referenced as `/works/…`.

## Content blocks

Files saved as `.mdx` can use these without importing anything. They all share
one visual language, so any combination stays consistent.

```mdx
<Prose title="Abstract">
Markdown paragraphs go here.
</Prose>

<Compare
  before={{ title: "The normal way", steps: ["One", "Two"] }}
  after={{ title: "Using X", steps: ["One", "Two"] }}
/>

<Features items={[{ title: "Fast", body: "Why it's fast." }]} />

<Stats
  title="Visits of People"
  period="2009 Feb — 2011 Jan"
  items={[{ value: "39,409", label: "Avg. Use of Day" }]}
/>

<Steps title="How to play" items={["First rule", "Second rule"]} />

<Figure src="/works/x/shot.jpg" caption="Caption" />

<Gallery items={[{ src: "/works/x/a.jpg", caption: "Before" }]} />

<Callout href="/journal/">More information? Check out my blog.</Callout>
```

Plain markdown works alongside them — headings, lists, tables, code blocks and
blockquotes are all styled.

## Adding a journal post

Create a `.md` file in `src/content/journal/`:

```yaml
---
title: Your title
date: 2026-08-01
description: One or two sentences — used in listings, search results and RSS.
tags: ["three.js"]
draft: false        # true excludes it from the build
---
```

Rename to `.mdx` if you want the content blocks above.

## How the 3D works

One canvas sits behind every page, carrying `transition:persist` so the WebGL
context survives navigation. The particle field holds four target shapes as
separate geometry attributes:

| Shape | Stage |
|---|---|
| Fibonacci sphere | 0 |
| Loose nebula | 1 |
| Even lattice | 2 |
| Tilted wave plane | 3 |

The vertex shader interpolates between them from a single `uProgress` uniform,
so morphing costs the CPU nothing regardless of particle count.

Pages declare what the field should do via `data-scene` on `<main>`:

- `data-scene="scroll"` — section centres drive `uProgress` (the landing page)
- `data-scene="static" data-scene-stage="2"` — hold one shape

Work detail pages pick their stage from the category, so each category reads as
a visually distinct place. See `src/data/categories.ts`.

Particle count adapts to the device (`pickQuality()` in `src/scripts/site.js`):
72² low-end, 108² mid, 156² desktop.

## Performance

three.js loads as a separate chunk *after* first paint — it never enters the LCP
path. Measured on the production build (local, unthrottled):

| Metric | Value |
|---|---|
| LCP | 173 ms |
| CLS | 0.00 |
| TTFB | 12 ms |
| Lighthouse | Accessibility 100 · Best Practices 100 · SEO 100 |

Real-world numbers over a network will be higher; the useful signal here is
that CLS is structurally zero and the heavy chunk is off the critical path.

## Graceful degradation

- No WebGL, or `prefers-reduced-motion: reduce` → the canvas stays at opacity 0
  and a static CSS gradient takes over.
- Reduced motion also disables Lenis, all scrub animations and the card tilt.
- Rendering pauses while the tab is hidden.
- Filtering on `/works/` is purely visual — every card ships in the HTML, so it
  works for search engines regardless.

## Deploying to GitHub Pages

`.github/workflows/deploy.yml` builds and deploys on every push to `main` or
`master`. In the repo: **Settings → Pages → Source → GitHub Actions**.

### Setting the domain

The domain is defined in exactly one place: the `SITE` constant at the top of
`astro.config.mjs`. Change that line and everything follows — canonical URLs,
Open Graph tags, sitemap, RSS, and `dist/CNAME` (generated by
`src/pages/CNAME.ts`, so it can never drift out of sync).

```js
const SITE = "https://your-domain.tw";   // protocol, no trailing slash
```

It currently reads `https://example.com`, a placeholder. GitHub Pages won't
verify that, so it has to be set before going live.

### DNS

For an apex domain (`example.tw`), either an `ALIAS`/`ANAME` record pointing to
`<username>.github.io`, or four `A` records to GitHub's IPs:

```
185.199.108.153
185.199.109.153
185.199.110.153
185.199.111.153
```

For a subdomain (`www.example.tw`), a single `CNAME` to `<username>.github.io`.

Once the certificate is issued, enable **Enforce HTTPS** in Settings → Pages.
Whichever form you pick — apex or `www` — must match `SITE` exactly, or
canonical tags will point somewhere the visitor isn't.

## Contact links

The Contact section renders `CONTACT_LINKS` from `src/data/links.ts` — no form,
no backend, nothing to maintain. Add, remove or reorder entries there:

```ts
{ label: "GitHub", value: "github.com/handle", href: "https://github.com/handle" }
```

`value` is what the visitor reads; `href` is where it goes. Anything starting
with `http` opens in a new tab automatically, `mailto:` links don't.
